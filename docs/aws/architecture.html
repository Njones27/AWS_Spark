Spark on AWS

Spark is a game-like web app that teaches students how AWS services fit together. This design hosts it on AWS straight from the GitHub repo with CDK, adds a small backend for cross-device progress and short share links, keeps the bill near zero and latency low, and puts every account-specific value in config so the whole stack can move to another AWS account.

Architecture

One CloudFront distribution is the only public entry point. It serves the built app from a private bucket and sends /api/* to a single Lambda function behind an HTTP API, so the app and its API share one origin and need no CORS.

Everything runs in us-east-1. Kentucky users are about 20 ms away, CloudFront certificates must live there anyway, and one region means no cross-region plumbing.

Request flows

localStorage stays the source of truth on the device. Sync runs in the background, so the UI waits on the API only for share and recover, and the app keeps working when a school network blocks /api.

First page load

Every visit. Static files only.

  1. CloudFrontGET / lands on the nearest edge location, 20 to 50 ms to first byte.
  2. CloudFront → S3The edge returns its cached index.html, or fetches it from the private bucket through OAC.
  3. BrowserHashed files under /assets/ download once and stay cached for a year.
  4. BrowserThe app boots from localStorage. Playing needs no API call.
FilesCache-Control
assets/**public, max-age=31536000, immutable
index.html, icons/, favicon.svgpublic, max-age=0, s-maxage=86400, must-revalidate

Edges keep index.html for a day and browsers revalidate it. Each deploy invalidates /* (one path, inside the 1,000 free a month). Both uploads use prune: false, so a student holding yesterday's index.html can still fetch its fonts and chunks.

Progress sync with a Builder Key

Background and debounced. Never blocks play.

  1. BrowserThe first finished level or saved Playground design calls POST /api/profiles. Profiles are created lazily, never on first visit.
  2. LambdaReturns profileId, a random 256-bit token and a builderKey. The app keeps token and key in localStorage beside the zustand state.
  3. BrowserAfter each change, a ~2 s debounce sends PUT /api/profiles/me with Authorization: Bearer <token> and the whole state.
  4. Lambda → DynamoDBMerges into PROFILE#<id>. completed becomes the set union (stored order first); band, playground and unlockAll take the request's values; updatedAt is server time.
  5. BrowserReplaces its copy with the merged state from the response. On load, GET /api/profiles/me does the same.

Two devices never lose a finished level. A blocked API, a 5 s timeout or a 429 means the client retries later while localStorage keeps working.

Short share link

One visible wait, with a fallback.

  1. BrowserShare in the Playground posts the existing encodeDesign code to POST /api/shares.
  2. LambdaAccepts it only if decodeDesign(code) returns a design, using the same src/engine/share.ts bundled by esbuild. Otherwise 400; over 16 KB, 413.
  3. DynamoDBStores SHARE#<id> with a 2-year TTL. The response is a 10-character id.
  4. BrowserShows https://<host>/#/s/<id>. It is a hash route, so CloudFront needs no rewrite and base: './' stays.
  5. BrowserOpening the link calls GET /api/shares/{id}, gets {code}, then behaves exactly like #/playground?d=<code>.

If the POST fails, the dialog shows the long #/playground?d= link instead, which works with no API at all.

Continue on another device

The Builder Key is all a student carries.

  1. BrowserOn the new device the student types the key into Continue my progress, for example MAPLE-OTTER-4821.
  2. LambdaPOST /api/profiles/recover normalises it (trim, uppercase, spaces and underscores become -) and hashes it with SHA-256.
  3. DynamoDBKEY#<keyHash> points to the profile. An unknown key gets 404.
  4. LambdaIssues a fresh token and invalidates the old one, then returns the profile and its state.
  5. BrowserStores the new token and applies the state. Normal sync resumes.

Recover is tightly throttled per route, with backoff per key prefix. It is not limited per IP, because a whole school sits behind one NAT address.

Components

Every piece is serverless and billed per use, so an idle stage costs close to nothing.

Considered and set aside

  • Lambda Function URL behind CloudFront with OAC. Cheaper (no $1/M), one fewer hop, IAM-locked via FunctionUrlOrigin.withOriginAccessControl. But every POST/PUT must carry x-amz-content-sha256, there is no stage throttling (reserved concurrency becomes the cap), and the function must live in the Web stack. Kept as a one-stack swap.
  • Amplify Hosting. Same services underneath, less control over caching and CSP, harder to move between accounts.
  • CDK Pipelines on CodePipeline. The owner wants GitHub as the pipeline.
  • Cognito for students. See Identity below.
  • No backend at all. An 8-character save code (band + completed levels) would cover progress, but not saved Playground diagrams, short share links or future coordinator rosters. The backend buys exactly those three.

Identity without student accounts

Students are never asked for a name, email or password. The API issues an anonymous profile, and a short Builder Key is the only thing a student carries to another device.

Why not Cognito for students

  • K-5 students often have no email address.
  • Passwords are friction on shared Chromebooks.
  • Districts often block Google sign-in for under-18s.
  • Collecting names or emails from under-13s pulls in COPPA consent rules.

MAPLE-OTTER-4821

word · word · four digits

Two different words from a 1,000-word kid-safe list (animals, plants, colours, weather, food, everyday objects) plus four digits, about 1010 combinations. It arrives with a random 256-bit bearer token. Both stay in localStorage, so the key can be shown again on that device.

Stored

  • SHA-256 of the token and of the normalised key, never the raw values
  • The progress blob: band, completed, playground, unlockAll
  • createdAt, updatedAt, and a TTL two years after the last write
  • Shared designs: the code and createdAt, TTL two years

Never stored

  • Names, emails or passwords
  • IP addresses (none in the table)
  • Free text of any kind. The closed schema rejects unknown fields with 400.
  • The token or Builder Key in plain form

Reserved for coordinators (adults)

A Cognito user pool and an HTTP API JWT authorizer on /api/classes/*, class codes that link Builder Keys to a roster, and a reset-a-student's-key action. All additive: nothing above changes.

Security and privacy guardrails

  • The bucket is private behind OAC. The API answers only requests carrying CloudFront's origin header. HTTPS only.
  • Recovery is throttled with per-key backoff. No per-IP WAF rules, which would block whole schools behind one NAT.
  • Payload sizes are capped server-side with the same validators the client uses.
  • CloudFront and API access logs are kept 14 to 30 days for operations only. The app gets a one-line privacy note.
  • The GitHub deploy role's trust is pinned to repo and environment, and it can only assume CDK bootstrap roles.

Response headers policy (default behavior)

HSTS, nosniff, Referrer-Policy: strict-origin-when-cross-origin, and this CSP, report-only in dev first:

default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; font-src 'self'; connect-src 'self'; frame-ancestors 'none'; base-uri 'self'

API and data

Seven routes under /api, JSON in and out. Routes are registered in API Gateway with the /api prefix and CloudFront forwards the full path unchanged. docs/aws/CONTRACT.md is the shared spec for infra/, backend/ and src/.

Errors return { "error": "<code>", "message": "<short, kid-safe text>" } with bad_request 400, unauthorized 401, forbidden 403, not_found 404, payload_too_large 413 (bodies over 64 KB, codes over 16 KB) or internal 500. API Gateway's own 429 is treated like a network failure.

Progress state (closed schema)

interface ProgressState {
  band: Band | null;
  completed: string[];       // ≤ 500 level ids, /^[a-z0-9-]+$/, ≤ 32 chars
  playground: string | null; // an encodeDesign() code, ≤ 16 KB
  unlockAll: boolean;
}

Any unknown field anywhere in a body, or a wrong type, gets 400. Tokens are 32 random bytes (base64url). Share ids are 10 characters from [A-Za-z0-9].

CI/CD

GitHub Actions deploys both stages. Pull requests only build and test; a merge to main deploys dev, smoke-tests it, and waits for the owner's one-click approval before prod.

ci.yml, on pull requests to main

  • actions/setup-node reads .nvmrc (Node 24), then npm ci, typecheck, frontend + backend + infra tests, vite build, cdk synth for dev and prod.
  • No AWS credentials and no lookups in stacks, so PRs from forks of the public repo are safe.
  • Later: cdk diff against dev posted as a PR comment.

deploy.yml, on push to main or workflow_dispatch

  • permissions: id-token: write, contents: read; concurrency: deploy without cancel-in-progress.
  • aws-actions/configure-aws-credentials@v4 with vars.AWS_DEPLOY_ROLE_ARN and vars.AWS_REGION, then cdk deploy --all --require-approval never --context APP_CONFIG=config/app-config-dev.json.
  • Prod: environment prod, needs: dev, required reviewer = owner, deployment branch policy main (available on public repos on the Free plan).
  • The Mainline_shield ruleset already forces PR + review onto main, so deploy never commits. script/deploy_stacks.sh mirrors the workflow for break-glass use.

Moving to another AWS account

No code changes. Account IDs live only in infra/config/*.json and the GitHub environment variables.

  1. Bootstrap the new account. Run setup_initial.sh with the new profile: CDK bootstrap, OIDC provider, Cicd roles, the SSM parameter and the Lambda quota check.
  2. Point config at it. A PR edits Project.Account (and Region if wanted) in app-config-prod.json, plus GitHub.Repo in the account config if the repo changes owner.
  3. Swap the GitHub variables. In environment prod, update AWS_DEPLOY_ROLE_ARN and AWS_ACCOUNT_ID. The trust-policy sub claims do not change. Run deploy.yml.
  4. Copy the data. A short scan-then-batch-write script between the two profiles (kilobytes per profile), or a PITR export to S3 plus ImportTable if the table has grown.
  5. Move the hostname. Without a domain the *.cloudfront.net name changes, so keep the old distribution for 90 days with a CloudFront Function that 301s to the new host (browsers keep the # fragment). With a domain, create the hosted zone in the new account, lower TTLs a day early, flip the alias and repoint the registrar's nameservers.
  6. Retire the old account. Run destroy_stacks.sh there once everything is verified, and delete the retained prod table after 30 days.

The stage throttles and reserved concurrency are the cost guardrails; raise them in config if alarms show 429s.

RiskMitigation
1Share links and bookmarks bake in the *.cloudfront.net hostname, so the account move or a later domain breaks every link in the wild.Register the domain before any public launch. Until then, the 90-day 301 bridge from the old distribution.
2A deploy white-screens a student mid-session.prune: false, s-maxage plus invalidation, and a vite:preloadError handler that reloads once.
3A fresh account's Lambda concurrency quota (often 10) throttles the first classroom.Checked and raised in setup_initial.sh; alarm on throttles.
